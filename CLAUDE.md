## Commands

```bash
pnpm dev          # Next.js dev server on http://localhost:3000
pnpm build        # production build
pnpm lint         # ESLint 9 flat config (next core-web-vitals + typescript)
pnpm typecheck    # tsc --noEmit

pnpm db:push      # push src/db/schema.ts straight to the database (no migration files)
pnpm db:generate  # generate SQL migrations into ./drizzle
pnpm db:migrate   # apply migrations from ./drizzle
pnpm db:studio    # Drizzle Studio
pnpm db:seed      # upsert the starter catalog from src/db/seed-data.ts (resets stock quantities)

pnpm auth:generate  # regenerate src/db/auth-schema.ts from the Better Auth config (+ timestamptz patch)
pnpm auth:make-admin <email>  # give an existing user the admin role
pnpm orders:reconcile  # settle pending/processing orders older than 35 min from Stripe (missed webhooks)

pnpm test           # Vitest unit + component tests (no database)
pnpm test:int       # Vitest integration tests against the Postgres test database
pnpm test:all       # all Vitest projects
pnpm test:watch     # unit + component in watch mode
pnpm test:coverage  # all projects with v8 coverage
pnpm test:e2e       # Playwright (configured in a later phase)
```

See Testing below.

The package manager is pnpm, pinned through `packageManager` in `package.json`. Use `pnpm dlx` instead of `npx`. pnpm skips dependency build scripts unless they're allowed under `allowBuilds` in `pnpm-workspace.yaml`. esbuild (for tsx and drizzle-kit) and unrs-resolver (for eslint-config-next) are allowed there already, so add any new dependency that needs a postinstall step too.

Environment variables live in `.env` (template: `.env.example`): `DATABASE_URL` (local Postgres), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL`, `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`. `drizzle.config.ts` reads them with `dotenv/config`, and Next.js loads them itself.

## Architecture

Stack: App Router under `src/app`, TypeScript with the `@/*` → `src/*` path alias, Tailwind CSS v4 through `@tailwindcss/postcss` (no `tailwind.config`), Better Auth, and Drizzle ORM on PostgreSQL through `pg`.

**Database (`src/db/`)**
- `index.ts` exports a single `db`, a Drizzle node-postgres client. The `Pool` is cached on `globalThis` outside production so it survives hot reloads. Import `db` from `@/db` and never create another pool.
- `schema.ts` is the only schema entry point. `drizzle.config.ts`, the `db` client (`drizzle(pool, { schema })`) and the Better Auth adapter all read from it. Every new table module must be re-exported from `schema.ts`, or drizzle-kit and relational queries won't see it.
- Schema changes go through versioned migrations: `db:generate`, review the SQL in `./drizzle`, then `db:migrate`, and commit the migration. Don't use `db:push` on tables that hold data.
- Store money as integer cents (`price_cents`), never as floats or `numeric`. `formatPrice` takes cents.
- Stock lives in `product_stock` (1:1 with `products`), not as a column on `products`, so it can move to variants later.
- Catalog queries live in `src/lib/products.ts` (`server-only`), the only storefront module that imports `@/db`. Add new reads there and call them from Server Components. `src/lib/catalog.ts` must stay client-safe (types and pure helpers), so it never imports `@/db`.
- Pages that read the database set `export const revalidate = 60`. Without it they're prerendered once at build with stale stock. This also means `next build` needs a reachable database.
- `auth-schema.ts` is generated by `pnpm auth:generate`, so don't edit it by hand. It holds the Better Auth tables (`user`, `session`, `account`, `verification`). The generator only emits timezone-less `timestamp` columns, so `auth:generate` runs `src/db/patch-auth-schema.ts` afterwards to switch them to `withTimezone: true` like the catalog tables. Keep that step when changing the script.

**Design system (`src/styles/`, `src/components/ui/`)**
- `src/app/globals.css` only imports Tailwind and three layers: `tokens.css` (the `@theme` tokens), `base.css` (element defaults) and `utilities.css` (`@utility` primitives such as `btn-*`, `container-*`, `grid-products`, `media-frame`, `text-label` and `link-reveal`).
- Tailwind's default colors, type scale and radii are reset with `initial`, so only project tokens exist: `ink`, `ink-muted`, `canvas`, `surface`, `line`, and so on. Stock classes like `text-gray-500` or `rounded-lg` produce nothing.
- Responsive layout values (`--gutter`, `--section-y`, `--grid-gap`, `--header-height`) are CSS variables on `:root` that change at breakpoints. They're exposed as spacing utilities: `px-gutter`, `py-section`, `gap-grid`, `h-header`.
- The look is monochrome and light-only, with square corners, hairline borders, uppercase tracked labels, Geist sans for UI and Cormorant Garamond serif for display headlines only.
- `src/components/ui` wraps these utilities in React components. Class names must appear in full in the source, never built like `` `btn-${x}` ``, or Tailwind won't generate them.

**Auth (`src/lib/`, `src/app/api/auth/`)**
- `lib/auth.ts` is the server-side Better Auth instance. It uses the Drizzle adapter with `provider: "pg"` and the full schema, has email and password sign-in enabled, and includes the `nextCookies()` plugin so server actions can set auth cookies. That plugin should stay last in `plugins`.
- `app/api/auth/[...all]/route.ts` mounts Better Auth's GET/POST handlers at `/api/auth/*`.
- `lib/auth-client.ts` is the React client (`authClient`), which points at `NEXT_PUBLIC_APP_URL`. Use it only in client components. Server code should call `auth.api.*` directly.
- When you change the Better Auth config (plugins, user fields), rerun `auth:generate`, then `db:generate` + `db:migrate`.
- Sessions last 30 days (sliding) with a 5-minute signed cookie cache. Email and password is the only sign-in method.
- `user.role` is a Better Auth additional field (`"customer"` by default, or `"admin"`) with `input: false`, so no auth endpoint can set it. Grant it with `pnpm auth:make-admin`.
- `lib/session.ts` (`server-only`) is the server-side entry point: `getSession()` (memoized per request), `requireSession(returnTo)` (redirects to `/sign-in?next=…`) and `requireAdmin()` (skips the cookie cache, 404s for non-admins). Call one at the top of **every** protected page and server action. Layouts aren't enough.
- `src/proxy.ts` redirects `/account/*` and `/admin/*` when there's no session cookie. That check is optimistic only (it never hits the DB), so it's never the real check.
- Don't read the session in shared UI like `SiteHeader`. That would make every catalog page dynamic.
- Pass any `?next=` redirect through `safeNext()` from `lib/redirects.ts` (it allows same-origin paths only).

**Bag (`src/lib/bag*.ts`, `src/app/bag/`, `src/components/bag/`)**
- The shopping bag is a cookie (`atelier_bag`, e.g. `12:2,15:1`) that holds product IDs and quantities **only**. There's no table yet, and guests and signed-in customers share the same mechanism.
- Prices, names and stock are always read live through `getBagProducts()` in `lib/products.ts`, never from the client. `lib/bag-server.ts` (`server-only`) owns cookie reads and writes and `getBag()`. `lib/bag.ts` is client-safe (types, parsing, `subtotalCents`).
- `app/bag/actions.ts` (`addToBag`, `updateBagQuantity`, `removeFromBag`) validates every argument and clamps quantities to live stock. `/bag` displays `min(quantity, stock)` and flags the difference, because it can't rewrite the cookie during render.
- The bag doesn't reserve stock. Checkout re-checks stock and reserves it in a transaction (see Checkout).
- The header count comes from `BagLink`, which reads the cookie in the browser so `SiteHeader` stays static. Client bag controls go through `useBagAction`, which dispatches the `bag-change` event that `BagLink` listens for.

**Checkout (`src/lib/orders.ts`, `src/lib/checkout.ts`, `src/app/checkout/`, `src/app/api/webhooks/stripe/`)**
- Stripe-hosted Checkout (Checkout Sessions, inline `price_data`). There's no Stripe product catalog: names and prices come from Postgres, and the design is in `docs/plans/2026-10-06-stripe-checkout.md`.
- `lib/orders.ts` (`server-only`) owns everything that touches orders or Stripe. `lib/checkout.ts` is client-safe (types, `decideTransition`, line building). `lib/stripe.ts` creates the client lazily, so `next build` needs no key.
- `startCheckout` takes no arguments. It locks the `product_stock` rows (in product ID order), clamps the bag to stock, decrements stock and inserts a `pending` order with price snapshots in one transaction. Then it creates the session (idempotency key `checkout-<orderId>`, 31-minute expiry) and redirects. If creating the session fails, the order is marked `failed` and its stock released.
- Stock is **reserved** while an order is `pending`/`processing`. `releaseOrder` returns it once (guarded by `stock_released_at`) on expiry, async failure, cancel or a new checkout from the same browser (`atelier_checkout` httpOnly cookie).
- Only Stripe moves an order to `paid`: the signed webhook, or the success page / `orders:reconcile` retrieving the session server-side. All three go through `applyCheckoutSession`, which locks the order and checks `amount_total`/currency (a mismatch means `needs_review`). Never mark an order paid from anything the browser sends.
- The webhook records `stripe_events.id` in the same transaction as the order change (duplicates are skipped). Errors return 500 so Stripe retries.
- Local webhooks: `stripe listen --forward-to localhost:3000/api/webhooks/stripe`. Env: `STRIPE_SECRET_KEY` (sandbox restricted key) and `STRIPE_WEBHOOK_SECRET`.
- Scripts that import `server-only` modules run with `tsx --conditions=react-server` (see `orders:reconcile`).
- Order history (`/account`, `/account/orders/[orderId]`) only reads through `getCustomerOrders`/`getCustomerOrder`, which filter by `user_id` in SQL. Another customer's order is a 404. Only placed orders are listed (`paid`, `processing`, `needs_review`, and `failed` with a payment intent); open or abandoned checkouts aren't orders.

## Testing

Strategy and phases: `docs/plans/2026-10-06-testing-strategy.md`. New features ship with tests.

- Tests live in `tests/`, organized by scope. Inside each scope folder, mirror the `src/` path of the code under test (e.g. `src/lib/checkout.ts` → `tests/unit/lib/checkout.test.ts`). Import app code through `@/…` and helpers through `@tests/helpers/…`.
  - `tests/unit/`: `*.test.ts` runs in the Vitest **unit** project (pure, client-safe helpers, no DB). `*.test.tsx` runs in the **component** project (jsdom + Testing Library, only for client components with logic).
  - `tests/integration/`: `*.test.ts` runs in the **integration** project (real Postgres, one file at a time).
  - `tests/e2e/`: Playwright (Phase 8).
  - `tests/helpers/`: setup files and shared helpers, never tests.
- Integration tests take only `DATABASE_URL` from the environment: the shell (CI), otherwise `.env.test` (template: `.env.test.example`), **never `.env`**. It must name a database ending in `_test`, or the run refuses to start. Stripe, Better Auth and app-URL variables are fixed dummies in `vitest.config.mts` that override `.env.test` and the shell, so tests never use real keys. The global setup creates the database if it's missing and applies `./drizzle` migrations, so run `db:generate` before testing a schema change.
- Every integration test starts with all tables truncated (identities restarted), empty cookies and unstubbed Stripe (`tests/helpers/setup-integration.ts`). Build data with `tests/helpers/factories.ts`; don't depend on the seed catalog.
- Use a real Postgres, never a mocked Drizzle. Mock only at the boundaries, which the integration setup already does:
  - `next/headers` → `tests/helpers/next-headers.ts`: seed or inspect cookies with `testCookies`; `headers()` carries the jar as a `cookie` header.
  - `@/lib/stripe` → `tests/helpers/stripe.ts`: stub calls on `stripeMock` per test (unstubbed calls reject). Build sessions and events with `makeCheckoutSession`/`makeEvent`, and webhook requests with `signedWebhookRequest`, which uses real SDK signatures.
  - Assert `redirect()`/`notFound()` with `expectRedirect`/`expectNotFound` from `tests/helpers/navigation.ts`.
- `server-only` is aliased to an empty module in tests, so server modules import directly.
